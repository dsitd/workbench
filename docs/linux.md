# Workbench на macOS и Linux

Один исходный код и агентный цикл. Основная Linux-цель: Ubuntu 24.04+ и Debian 12+, x86_64 или arm64. Для разработки нужны Node.js 22.12+ и npm. Для бенчмарков также нужен Python 3. Существующие `node_modules` и готовые пакеты между ОС не копируются: зависимости устанавливаются заново.

## Установка на Ubuntu/Debian

```sh
sudo apt-get update
sudo apt-get install bubblewrap libsecret-1-0 gnome-keyring git python3
npm ci
npm run dev
```

Для запуска из исходников также нужны библиотеки Electron: на Ubuntu 24.04 `sudo apt-get install libgtk-3-0t64 libnss3 libasound2t64 libgbm1`, на Debian 12 `sudo apt-get install libgtk-3-0 libnss3 libasound2 libgbm1`. В обычной графической установке многие из них уже присутствуют.

Запускайте приложение обычным пользователем в графической сессии. GNOME Keyring нужен для сохранения ключей в настройках; на KDE можно использовать KWallet. Если хранилище не разблокировано или Electron выбрал `basic_text`, приложение откажется сохранять ключ. Альтернатива: пользователь задаёт переменную окружения и указывает её имя в настройках модели. Значения не передаются командам агента. [Механизм Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage).

Системный Bubblewrap должен поддерживать `--disable-userns` (0.8+) и иметь разрешение хоста на создание пользовательских пространств имён. Наличие исполняемого файла проверяется настоящим пробным запуском. Если политика AppArmor или контейнера запрещает изоляцию, команды, Git и stdio MCP будут недоступны; автоматического запуска без изоляции нет. Диагностика: `npm run sandbox:check`. Не запускайте Workbench через `sudo` или с `--no-sandbox`.

## Пакеты

```sh
npm run package       # распакованное приложение для текущей ОС
npm run dist          # macOS: DMG/ZIP; Linux: AppImage/DEB
```

Для явного выбора есть `package:mac`, `package:linux`, `dist:mac`, `dist:linux`. Нативную сборку и проверку Linux выполняйте на Linux, macOS — на macOS. Результаты находятся в `release/`. Пакеты локальные, неподписанные, публикация отключена. Поле maintainer у локального DEB использует явно фиктивный адрес `example.invalid`; перед публичным выпуском его нужно заменить контактным адресом проекта.

DEB объявляет зависимость от Bubblewrap и библиотек Electron; устанавливается через `sudo apt install ./release/<имя-пакета>.deb`. Для AppImage системные зависимости устанавливаются отдельно; если в системе нет FUSE, можно использовать стандартный режим `--appimage-extract-and-run`. На Ubuntu с ограниченными user namespaces предпочтителен DEB и разрешённая системным администратором конфигурация Electron/Bubblewrap.

На Linux данные по умолчанию находятся в `~/.config/Workbench`, на macOS — в `~/Library/Application Support/Workbench`. Ключи из системного хранилища одной ОС нельзя переносить как готовые зашифрованные данные другой ОС: пользователь вводит их заново.

## Изоляция

`src/backend/sandbox/` — общий контракт запуска. macOS использует прежний профиль Seatbelt через `sandbox-exec` и zsh. Linux использует Bubblewrap и bash. Команды агента, Git и stdio MCP проходят через этот контракт; renderer остаётся в собственном Electron sandbox.

На Linux монтируются системные runtime-каталоги только для чтения, разрешённые папки проекта и отдельный временный каталог. Вложенные права применяются от родителя к потомку. Каталог приложения скрывается, а временные файлы и явно разрешённые skills открываются отдельно. Существующие защищённые файлы маскируются без чтения содержимого; защищённые символические ссылки и чрезмерно большой обход приводят к отказу запуска. Git получает только очищенные метаданные и объекты, без hooks, config и alternates. Сокеты и специальные файлы внутри проекта скрываются.

Без разрешения интернета создаётся отдельное сетевое пространство имён. С разрешением интернета используется сеть хоста. Окружение процессов формируется явно; пользовательский HOME и сессионная D-Bus-шина не передаются. [Контракт Bubblewrap](https://github.com/containers/bubblewrap/blob/main/README.md).

Ограничения различаются по механизму: macOS запрещает защищённые имена динамическим правилом, Linux маскирует существующие пути перед запуском. Новый файл с защищённым именем, созданный во время команды, не получает отдельную маску до следующего запуска. Не добавляйте секретные файлы в рабочую папку во время активной команды или MCP-сессии. Файловые инструменты дополнительно проверяют защищённые имена при каждом обращении.

## Проверки и бенчмарки

```sh
npm run check
npm run sandbox:check
npm run smoke
npm run bench:check
```

`check` выполняет TypeScript, модульные тесты, тесты бюджетного шлюза и сборку. `sandbox:check` проверяет реальные команды, права, сеть и откат. `smoke` проверяет интерфейс Electron с локальными ответами. `bench:check` проверяет настоящий цикл агента: чтение, правку, команду и автоматическую проверку. Платные модели и существующие ключи для этих проверок не нужны. `.github/workflows/check.yml` запускает эти проверки на macOS и Ubuntu; нативная проверка изоляции обязана пройти, а не пропускается.

Основной runner и проверка памяти работают под обычным Node, без Electron/графической сессии:

```sh
npm run bench -- --dry-run --arms workbench --manifest /absolute/path/manifest.json
npm run bench:memory -- --dry-run --arms workbench
```

Для сравнения с Pi: `--arms workbench,pi`, публичные зависимости Pi 1.1.0 в `--pi-dir /absolute/path` либо в `.workbench/comparison/pi`. Используйте отдельную установку зависимостей для каждой ОС. `--base` меняет каталог данных, `--node` и `--python` выбирают интерпретаторы, `--swe-runtime` задаёт отдельный runtime SWE. В Linux Pi получает доступ только к локальному бюджетному шлюзу через Unix-сокет и relay внутри изолированной сети.

В dry-run модель возвращает заглушку без решения: `tests=false` ожидаемо. Для реального запуска нужен отдельно разрешённый бюджет с прежним накопительным реестром. Под Node имя переменной с ключом передаётся через `--credential-env OPENROUTER_API_KEY`; значение задаёт пользователь. При запуске собранного runner через Electron можно использовать локальное хранилище Workbench. Dry-run не открывает vault. Не удаляйте реестры расходов и резервы неизвестных запросов.

Замороженные результаты и bundles прежних кампаний сохраняют исходную платформу. Разовые контроллеры исторических кампаний (`noncoding`, `everyday`, `web-desktop`, `refactor`) не являются переносимыми точками входа. Старые fixtures с абсолютными путями macOS требуют отдельной переносимой версии; не переписывайте их внутри завершённого эксперимента. Для сравнения качества фиксируйте версии задач, Python/Node, модели и бюджета; отчёт новых runners содержит ОС и архитектуру.
